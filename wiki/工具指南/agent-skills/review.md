# Agent Skill — Code Review and Quality (`/review`)

## 触发词

`/review`、"代码审查"、"CR"、"review 一下这段代码"、"审查这个 PR"

## 核心原则

**每次合并前都要审查——没有例外。AI 生成的代码需要更多审查而非更少。**

## 五轴审查

| 轴 | 关注点 |
|----|--------|
| **1. 正确性** | 符合 spec？边界处理？错误路径？差一错误？ |
| **2. 可读性** | 命名清晰？逻辑直接？无过度设计？能否用更少代码？ |
| **3. 架构** | 遵循现有模式？模块边界清晰？抽象级别适当？ |
| **4. 安全性** | 输入验证？无密钥泄露？认证检查？SQL 注入？ |
| **5. 性能** | N+1 查询？无界循环？异步阻塞？分页？ |

## 问题严重性标注

| 前缀 | 含义 | 作者操作 |
|------|------|---------|
| *(无前缀)* | 必须修复 | 合并前必须解决 |
| **Critical:** | 阻塞合并 | 安全漏洞、数据丢失、功能损坏 |
| **Nit:** | 轻微、可选 | 作者可忽略 |
| **Optional:** | 建议 | 值得考虑但非必须 |

## 变更大小指南

- ~100 行 → 好，一次审查搞定
- ~300 行 → 可接受（单一逻辑改动）
- ~1000 行 → 太大，需要拆分
