# Agent Skill — Test-Driven Development (`/test`)

## 触发词

`/test`、"写测试"、"TDD"、"跑一下测试"、"测试驱动"、"修复这个 bug"

## 核心原则

**测试就是证据——"看起来对"不等于完成。**

## 场景 A: 新功能 — TDD 循环

```
    RED                GREEN              REFACTOR
 写失败的测试 ──→ 写最小代码通过 ──→ 重构实现  ──→  (重复)
```

## 场景 B: Bug 修复 — Prove-It 模式

```
收到 bug 报告
    │
    ▼
写一个复现 bug 的测试（必须失败）
    │
    ▼
确认测试失败（证明 bug 存在）
    │
    ▼
实现修复
    │
    ▼
确认测试通过（证明修复有效）
    │
    ▼
跑完整测试套件（无回归）
```

## 测试金字塔

```
          ╱╲
         ╱  ╲         E2E 测试 (~5%)
        ╱    ╲        完整用户流程
       ╱──────╲
      ╱        ╲      集成测试 (~15%)
     ╱          ╲     组件交互、API 边界
    ╱────────────╲
   ╱              ╲   单元测试 (~80%)
  ╱                ╲  纯逻辑、隔离、毫秒级
 ╱──────────────────╲
```

## 写好测试的原则

1. **测试状态而非交互** — 断言结果，而非内部方法调用
2. **DAMP 优于 DRY** — 每条测试讲完整故事
3. **偏好真实实现而非 Mock** — 真实 > Fake > Stub > Mock
4. **Arrange-Act-Assert** — 设置场景 → 执行动作 → 验证结果
5. **一个概念一个断言** — 每条测试只验证一个行为

## 反借口

| 借口 | 反驳 |
|------|------|
| "写完代码再补测试" | 你不会补的。事后写的测试测的是实现而非行为 |
| "这个太简单不值得测" | 简单代码会变复杂。测试记录了预期行为 |
| "我手动测过了" | 手动测试不能持久 |
